# DashBar · адаптивный профиль и приёмка

В «Приёмке» откройте «Источники и загрузка по ссылке». Очередь
показывает имя и источник документа. Выберите «Накладная» или
«Матрица цен» и нажмите «Загрузить». При успешном сохранении запись
снимается с очереди. Если проверки не прошли, файл остаётся в очереди.

«Прямая ссылка на файл» работает и в автономном index.html, когда
сервис отдаёт файл по HTTPS без авторизации и разрешает запрос
из браузера (CORS). Для папок Drive, Google Таблиц и серверных
интеграций запускайте приложение по инструкции ниже.

## Реестр накладных

Накладные поступают через подключённую очередь и прямые ссылки.
В реестре можно искать по поставщику, товару, номеру или имени файла.
В запросе можно совместить поставщика и товар. Нажмите на накладную,
чтобы раскрыть товарные строки. При большом списке нажмите
«Показать ещё» в реестре или «Показать следующие документы» в очереди.
Матрицу цен можно загрузить локальным файлом.

## Приход товара

После проверки накладная появится в реестре. Откройте её, нажмите
«Поставить на приход» и подтвердите, что все строки относятся к бару.
В «Склад → Приходы в DashBar» появится движение. Повторное проведение
одной накладной блокируется. Датированный снимок остатков считается
остатком на конец дня. Приходы на дату снимка и раньше требуют
сверки в учёте, поскольку могли уже попасть в выгрузку.

Приход относится к внутреннему складу DashBar. Синхронизация
остатков с iiko и запись проводок в внешнюю систему в этой сборке
отсутствуют.

Во всех поддерживаемых источниках закупочная цена единицы рассчитывается
из полной суммы строки и фактического количества. Указанная цена нужна
для сверки, а не является обязательной колонкой. Если сумма отсутствует,
вычисление из напечатанной цены помечается как расчётное. Явно указанную
стоимость без НДС не подменяем стоимостью с НДС; при неизвестной налоговой
основе сохраняем исходную сумму без предположений о ставке.

В реестре «Сопоставить со складом» позволяет проверить адрес грузополучателя
и сопоставить позиции с точными названиями загруженного склада. При OCR
подсказки используют название в кавычках, транслитерацию, OCR-омографы,
фасовку и историю подтверждённых сопоставлений данного поставщика.
Например, «Корона» соответствует Corona Extra, но не Corona Cero;
Heidegger Hell — «Хайдеггер Хель». Нечёткие совпадения требуют выбора
пользователя и не объединяют складские карточки автоматически.
В профиле можно указать адрес этого
бара; при нескольких заведениях без обоих адресов или при несовпадении
приход блокируется до сверки. Эта сборка по-прежнему поддерживает один
рабочий профиль, а не автоматическую маршрутизацию между заведениями.

Объём и фасовка выделяются только из читаемых обозначений: например,
30 бутылок по 0,75 л — 22,5 л, даже если фасовка составляет 6 бутылок.
Если единица исходного документа — упаковка и указано 6×0,75 л, пять
упаковок дают 30 бутылок и 22,5 л. На новый складской приход предлагаются
литры, килограммы либо штуки; при сопоставлении используется единица
существующей складской позиции. Сохранённые движения не пересчитываются
задним числом. В выводе остатков стоимость показывается только для
позиций, полностью сформированных известными приходами DashBar.

## ЭДО и DocsInBox

В разделе «Приёмка → Источники и загрузка по ссылке → Выгрузка ЭДО
или DocsInBox» выберите источник и пакет файлов. XML УПД продавца
открывается как черновик с суммами и НДС. Табличные выгрузки с товарными строками и поддерживаемыми колонками
идут через обычный импорт накладных.

XLS-выгрузка списка накладных DocsInBox с внутренними номерами,
поставщиками и итогами открывается как отдельный реестр. Сохраните
предпросмотр и используйте фильтр «Только группы с разными суммами».
Совпадения группируются по номеру поставщика, дате и покупателю.
Для идентификации поставщика используется ИНН, если он есть в выгрузке.
Товарные остатки этот реестр не меняет. Для прихода нужен оригинал
с наименованиями товаров, единицами и количеством.
Подписанные архивы, корректировочные документы и шаблоны с другой
структурой требуют отдельного разбора.

Для автоматической подачи из настроенного экспорта используйте свою
папку Google Drive или передавайте каждый выгруженный файл во входящий
API с параметром source=docsinbox либо source=edi. Этот способ требует
настроенной передачи файла на стороне источника. Прямой опрос
DocsInBox с авторизацией поставщика в этой сборке не подключён.

## Структура приложения

index.html подключает независимые файлы интерфейса из каталога modules.
core отвечает за состояние, dashboard за стартовый сценарий, receiving
за очередь и оформляемые документы, warehouse за остатки и приход,
documents за импорт файлов, assistant за помощника. Техкарты, отчёты,
общий контроллер и запуск имеют собственные файлы. Стили вынесены
в assets/app.css. В серверной части app.py подключает очереди и API,
ocr.py читает сканы, edi.py разбирает XML.

## Профиль и файлы

Откройте index.html из распакованной папки. Excel-модуль находится
в assets/xlsx.full.min.js. Анкета задаёт следующий шаг на экране
«Сегодня». Ответы можно пересмотреть из этого экрана или из настроек.
Склад определяется по выгрузке остатков; если в ней несколько складов,
оператор выбирает нужную колонку.

Предпросмотр распознаёт складскую выгрузку и оборотно-сальдовую
ведомость по отдельному складу, бланк инвентаризации с двумя
строками заголовков и листы с однозначной колонкой закупочной цены.
Для сверки факта нужны учётные остатки того же склада и даты.

При вводе факта задним числом учёт включает проведённые приходы
по выбранную дату. Если по позиции уже загружен более поздний остаток,
приложение сохраняет исторический факт отдельно. Учёт и разница в такой
строке остаются пустыми до сверки со сличительной ведомостью на нужную дату.

## Один HTML-файл

`DashBar-offline-ru.html` открывается как локальная страница в браузере.
В него включены интерфейс, обработка Excel и CSV и локальный помощник.
При просмотре через файловый менеджер или чат откройте скачанный файл именно
в браузере. Если приложение просмотра ограничивает JavaScript, используйте
адрес локального сервера.

Чтобы открыть одну версию с телефона, планшета и компьютера, подключите их
к одной доверенной Wi-Fi-сети. Из папки `source/` запустите:

```sh
python3 tools/serve_standalone.py ../DashBar-offline-ru.html --host 0.0.0.0 --port 8765
```

На Windows вместо `python3` можно использовать `py -3`. На том же компьютере
откройте `http://127.0.0.1:8765/`. На телефоне и планшете замените адрес
на IPv4 компьютера в Wi-Fi-сети. Если он недоступен, проверьте, что сеть
разрешает подключение между устройствами и что выбранный порт доступен
из этой сети. Профили хранятся отдельно в каждом браузере. JSON-копия
в «Профиле и настройках» переносит данные между устройствами, браузерами
и адресами запуска. Для сканов и интеграций используйте серверную сборку.

Пересобрать HTML из `source/` можно командой
`python3 tools/build_standalone.py ../DashBar-offline-ru.html`.

## Тестовый сервер в GitHub Codespaces

Откройте нужную ветку в GitHub и создайте Codespace из меню **Code → Codespaces**.
Дождитесь установки зависимостей. Для пилота используйте закрытый порт в
панели **Ports** и отдельную очередь тестового стенда.

Перед первым запуском задайте `BM_ENCRYPTION_KEY` и `BM_OPERATOR_TOKEN` как
секреты Codespaces согласно инструкции ниже. Сохраните значения для повторного
запуска с той же очередью. Для закрытой папки Drive задайте путь
`BM_DRIVE_SERVICE_ACCOUNT` к файлу сервисного аккаунта в Codespace вне
репозитория. Дайте этому аккаунту только право чтения нужной папки.

После подключения секретов запустите сервер в терминале Codespace:

```sh
.venv/bin/python -m uvicorn app:app --host 0.0.0.0 --port 8765 --workers 1 --no-access-log
```

Откройте адрес порта 8765 из панели **Ports**. В разделе «Приёмка» подключите
очередь ключом оператора, затем настройте папку и начальную синхронизацию.
Codespace подходит для прогона пилота, пока рабочая среда запущена.

## Запуск на Windows

Распакуйте архив и откройте PowerShell в папке с `app.py`.
Нужен Python 3.11 или новее.

```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install -r requirements.txt
$env:BM_ENCRYPTION_KEY = & .\.venv\Scripts\python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
$env:BM_OPERATOR_TOKEN = & .\.venv\Scripts\python -c "import secrets; print(secrets.token_urlsafe(32))"
.\.venv\Scripts\python -m uvicorn app:app --host 127.0.0.1 --port 8765 --workers 1 --no-access-log
```

Значения `BM_ENCRYPTION_KEY` и `BM_OPERATOR_TOKEN` для рабочего прогона
сохраните в менеджере секретов. При повторном запуске задайте те же
значения. Новый ключ шифрования не сможет открыть старую очередь.
На Linux запуск аналогичен. Установите переменные окружения через
`export`, а интерпретатор виртуальной среды находится в `.venv/bin/python`.

Откройте http://127.0.0.1:8765 → «Свой бар» → «Приёмка» →
«Источники и загрузка по ссылке». Введите `BM_OPERATOR_TOKEN` в поле
«Ключ оператора» и нажмите «Подключить очередь». Этот ключ не отправляется
внешним системам.

## Распознавание сканов и фотографий

Для распознавания установите Tesseract и Poppler. Команды
`tesseract`, `pdfinfo` и `pdftoppm` должны быть доступны серверу через PATH.
В Debian и Ubuntu это пакеты `tesseract-ocr` и `poppler-utils`.
Сборка содержит модели `rus` и `eng` в каталоге `ocr-models/`.
Проверьте их командой `tesseract --list-langs --tessdata-dir ocr-models`.
Если сервер уже использует `TESSDATA_PREFIX`, в указанном им каталоге
должны быть доступны обе модели.

Менеджер кладёт фото или скан в подключённую папку либо отправляет фото
боту. Сервер помещает оригинал в очередь. Для фото нажмите «Распознать».
Для PDF нажмите «Открыть» как накладную. Если текстовый слой пуст,
приложение запросит локальное распознавание.

В предпросмотре проверьте оригинал и исправьте поля. Покупатель переносится из
подписанного поля скана или из XML УПД. Если распознавание оставило поле пустым,
внесите покупателя из оригинала. Если в документе этого поля нет, оставьте его
пустым. Введённый покупатель сохраняется в карточке и в JSON-копии. При необходимости
добавьте или удалите строки. Перед записью проверяются количество,
цена и сумма без НДС, НДС по строке, сумма с НДС и итог документа. Для строки
без НДС укажите 0. Если при чтении фото пропущена сумма с НДС,
приложение может предложить её по прочитанным полям, когда итог
документа сходится. Предложенная сумма помечена для проверки. Сверка закупочных цен распознанной накладной требует,
чтобы для сопоставимой позиции матрица явно обозначала цену с НДС.

PDF-сканы принимает по 1–4 страницы на документ. Табличная разметка
в первую очередь настроена на УПД. Другие бланки могут требовать
ручной проверки и заполнения полей по оригиналу. Документы обрабатываются
на сервере DashBar. Внешний распознаватель для этой версии не нужен.
В интерфейсе один рабочий режим менеджера. Подтверждение записи выполняет
пользователь, учётную систему приложение не изменяет.

Для обычной и расширенной формы УПД (с колонками количества в одном месте и количества
мест) сервер отдельно проверяет разметку таблицы и распознаёт ячейки в более
высоком разрешении. Если несколько вариантов чисел совпадают по арифметике,
предлагается только однозначный вариант с учётом прочитанного общего итога
и, когда доступны, итогов без НДС и НДС. Расчётные поля помечаются отдельно;
при неоднозначности финансовые поля остаются пустыми. ИНН извлекается только
из области продавца с проверкой контрольных цифр. Даже при совпадении сумм
требуется сверка названий, фасовок, единиц и реквизитов с оригиналом.
Расширенный разбор ограничен 16 строками на страницу и общим тайм-аутом OCR;
для других форм сохраняется прежний разбор или ручная сверка, предпочтительно
импортировать оригинал XML УПД из ЭДО.
Товарно-транспортная накладная без разбивки НДС требует соответствующего УПД
или счёта-фактуры для сверки закупочной цены; отсутствующий налог не вычисляется
из одного общего итога ТТН.
Для распознанной товарной таблицы формы 1-Т отдельно извлекаются количество
и сумма строки. Для черновика УПД налоговые реквизиты необязательны, но при
наличии проверяются. Независимый итог документа должен совпадать с суммой
строк; при неоднозначном OCR поля оставляются для проверки человеком.

## Google Drive

1. Включите Google Drive API в своём Google Cloud проекте. Для закрытой
   папки подключите сервисный аккаунт с правом чтения выбранной папки.
   Сохраните файл аккаунта вне каталога приложения и задайте его путь
   в `BM_DRIVE_SERVICE_ACCOUNT` до запуска сервера. Для доступной по
   ссылке папки можно использовать `BM_DRIVE_API_KEY`, если Google
   разрешает чтение через этот ключ. Доступ такой папки зависит от её
   настроек и ключа ссылки.
2. В «Источники и загрузка по ссылке → Папка Google Drive» вставьте ссылку на папку,
   при необходимости укажите дату изменения файла в Drive и отметьте подпапки.
   Если ссылка вставлена в поле прямой загрузки, серверная сборка перенесёт её в настройки папки.
   Для смешанной папки оставьте фильтр «Только файлы с пометкой „Бар“».
   Если в папке только барные документы без маркировки, снимите этот фильтр.
3. Нажмите «Подключить и загрузить документы». После первого прогона сервер
   опрашивает источник по заданному интервалу. Если Drive сообщает об отказе,
   проверьте право чтения папки у сервисного аккаунта сервера.
4. Поддерживаются PDF, Excel, CSV, TSV, TXT, JPG, PNG и WEBP.
   Для нативного листа воспользуйтесь загрузкой из Google Таблиц ниже.

[Поиск файлов Drive](https://developers.google.com/workspace/drive/api/guides/search-files) ·
[Загрузка файлов](https://developers.google.com/workspace/drive/api/guides/manage-downloads)

## Google Таблицы

Включите Google Sheets API в том же проекте Google Cloud. Для закрытой
таблицы дайте настроенному сервисному аккаунту право чтения таблицы.
Откройте нужный лист, скопируйте его ссылку и вставьте в поле
«Google Таблица». Если ссылка содержит `gid`, выбирается указанный
лист, иначе первый. Нажмите «Добавить лист в очередь». Это разовая
загрузка текущих значений листа. Для новой версии повторите действие.

[Чтение значений Google Таблиц](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/get)

## Telegram

Добавьте отдельного бота в нужный чат и обеспечьте, чтобы он получал
вложения. Для обычных сообщений группы это зависит от режима
конфиденциальности бота и его роли. В разделе «Telegram» укажите ID
конкретного чата и токен. Сервер запрашивает входящие обновления и
обрабатывает только вложения из указанного чата. Используйте либо этот
опрос, либо другой потребитель обновлений того же бота.

Отправляйте фото либо PDF, Excel и CSV как файлы до 20 МБ. Старую историю этот
режим не загружает. Для прогона отправьте новое вложение после настройки.
Повтор той же копии из Drive или Telegram не добавляет вторую запись
в очередь.

[Официальный Telegram Bot API](https://core.telegram.org/bots/api) ·
[Какие сообщения получает бот](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get)

## iikoCloud и другие сервисы

В «iikoCloud» введите App ID, Client Secret и API Key, затем нажмите
«Проверить и сохранить». Сервер выполняет проверку доступа к списку организаций. Импорт
из учётной системы идёт через экспорт файла или входящий API.

[Руководство iikoCloud по авторизации и организациям](https://api.iiko.help/docs/en/guides/organizations-and-terminals/)

Для сервиса, способного отправить файл HTTP-запросом, задайте отдельный
секрет `BM_PUSH_TOKEN`. Приёмник принимает файл как тело запроса.
Ключ приёма не даёт права просматривать очередь и документы.

```powershell
curl.exe -X POST "http://127.0.0.1:8765/api/intake/incoming?filename=invoice.csv" `
  -H "Authorization: Bearer $env:BM_PUSH_TOKEN" `
  -H "Content-Type: application/octet-stream" `
  --data-binary "@invoice.csv"
```

## Хранение и границы версии

Очередь и её настройки хранятся в `data/intake.sqlite3`. Файлы, их
названия и настройки интеграций шифруются с помощью `BM_ENCRYPTION_KEY`.
Журнал очереди сохраняет настройку источника, приём и отметку проверки.
Реестр и решения прототипа по-прежнему находятся в браузере. Если в нём
есть рабочие данные, экспортируйте JSON-копию в предыдущей версии и
восстановите её в новой. Страница на новом адресе имеет своё хранилище.

Сборка предназначена для локального запуска одного заведения с одним
процессом. Перед размещением для команды нужны HTTPS, вход пользователей
и проверка разделения заведений. Рабочие настройки источников задаются при запуске. Интеграции можно
проверить после настройки сервера и источников.

## Проверки

После установки зависимостей запустите `python -m unittest discover -s tests -v`
из корня проекта. Тесты проверяют разбор синтетического УПД и отказ
при неподдерживаемой валюте. Для проверки синтаксиса клиентских модулей
можно запустить `node --check` для каждого файла в `modules/`.

Для регрессии пользовательских сценариев запустите `node tests/workflows.cjs`
с Node.js 22 или новее. Тесты имитируют DOM, сеть и хранилище браузера.
Для регрессии серверной очереди запустите `python tests/queue_stress.py`.
Тест использует временную базу, сгенерированные ключи и имитацию ответов Google.

## Помощник с внешним ИИ

По умолчанию чат отвечает по локальным данным. Для тестового подключения
OpenAI Responses API задайте `BM_AI_OPENAI_KEY` и `BM_AI_OPENAI_MODEL`
в окружении сервера и перезапустите его. Укажите модель, доступную проекту
API. Затем подключите очередь ключом оператора. В разделе «ИИ» появится
кнопка «Спросить ИИ». Обычная кнопка и подсказки продолжают использовать
локальный режим.

Отдельная кнопка отправляет текст текущего вопроса и пять счётчиков
документов и записей. Файлы, история чата и содержимое складских строк
в запрос не добавляются. В журнал серверной очереди пишется только факт
обращения. При сбое отображается
локальный ответ. На результат распознавания и подтверждение прихода
ответ модели не влияет.

## Визуальное распознавание УПД

Локальный OCR остаётся первым этапом. Для повторного чтения неполных
черновиков укажите ключ сервера `BM_AI_OPENAI_KEY` и отдельно
`BM_INVOICE_VISION_MODEL` с именем доступной модели, которая принимает изображения
и поддерживает Structured Outputs в Responses API. После перезапуска
сервер сможет отправлять изображения страниц УПД на внешний API с
`store: false`. Оставьте `BM_INVOICE_VISION_MODEL` пустым для локальной
обработки.

Внешний ответ проходит проверку суммы строк и арифметики НДС. Черновик
из визуального режима требует ручного подтверждения. При недоступности
модели приложение показывает локальный черновик, если он получен.
Серверный журнал хранит факт обращения к API.
