# Перенос профиля DashBar в PostgreSQL

Миграция описана для пилота с несколькими барами. Текущая версия использует
JSON в браузере и SQLite для серверной очереди. Для первого запуска берём копии
этих источников и выполняем пробный импорт в отдельную базу.

## Модель данных

| Таблицы | Что переносим |
|---|---|
| venues, memberships, warehouses | Профиль и ответы анкеты, доступ менеджера и склады заведения |
| products, suppliers, supplier_prices | Номенклатуру, поставщиков и цены с единицей, базой НДС и датой |
| documents, invoices, invoice_lines | Источники, реквизиты, строки и ссылки на оригиналы |
| stock_snapshots, stock_snapshot_lines, stock_movements | Историю остатков и подтверждённые приходы |
| inventory_counts, inventory_lines | Черновики, завершённые пересчёты, фактические и учётные количества |
| operational_records | Техкарты, продажи, заказы, календарь и действия по находкам. На первом этапе храним их как JSONB с версией схемы |
| import_batches, audit_events | Контрольные суммы импортов, события пользователя и результаты сверки |

Первичные ID на сервере — UUID. Каждая запись, принадлежащая бару,
содержит `venue_id`. Составные внешние ключи включают `venue_id`, чтобы
строка одного бара не могла ссылаться на запись другого. Политики RLS
привязывают запрос к заведению и членству пользователя. Оригиналы хранятся
в закрытом объектном хранилище с шифрованием и серверной авторизацией.
Суммы и количества хранятся в `numeric`, даты документов — в `date`,
время аудита и подтверждения — в `timestamptz`.

## Идентификаторы и повторный запуск

- Каждому профилю заранее назначаем `venue_id`. Для старого объекта со
  стабильным ID генерируем UUIDv5 из идентификатора заведения, типа сущности
  и старого ID. Для сущностей, смоделированных как словари, сохраняем связь
  серверного ID с исходным ключом. Устойчивость ID проверяем повторным импортом.
- Снимок файла идентифицируем по SHA-256 в пределах заведения.
  Повтор файла и повтор бизнес-документа проверяются отдельно.
- Для документов сверяем зафиксированную логику прототипа по поставщику,
  дате и номеру. Если у одной записи есть ИНН, а у другой только имя, либо
  отсутствует один из реквизитов, потенциальное совпадение выводим в отчёт
  сверки. Исторические карточки автоматически не сливаем.
- Уникальность подтверждённого прихода контролирует ключ
  `(venue_id, invoice_id)` в заголовке движения. Запись движения, строк
  и аудита проводим в одной транзакции. Остатки сверяем с учётом даты
  исходного снимка.

## Пробный импорт и переключение

1. Экспортировать JSON и снять копию очереди SQLite. Сохранить контрольные
   суммы и количество записей. Настройки доступа задать в новой среде,
   исходные секреты и историю чата не импортировать.
2. Проверить схему JSON версий v1 и v2, единицы, даты, связи строк и
   дубли. Выдать список записей для сверки. Подтверждение пробного импорта
   выполняется только после проверки.
3. Импортировать в тестовую базу в транзакции и сравнить число документов,
   суммы накладных, остатки по позициям, черновики и ответы анкеты.
   Повторить запуск и подтвердить, что число записей осталось прежним.
4. Создать два тестовых заведения и проверить чтение, запрос оригинала
   и создание движения с идентификатором другого заведения. Все такие
   запросы должны завершиться отказом.
5. Согласовать окно переключения. Сохранить исходный JSON и копию базы.
   При откате до начала рабочих записей вернуть прежний адрес приложения.
   Если после переключения появились записи, сначала выгрузить изменения
   и сверить их перед возвратом, чтобы их не потерять.

На этой стадии схема и порядок переноса спроектированы. Код миграции,
проверка на PostgreSQL и переключение рабочих данных выполняются
следующим этапом.
